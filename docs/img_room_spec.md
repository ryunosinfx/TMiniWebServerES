## 1. 概要

チャット（`/ws/chat/<roomId>`）と同じトポロジーで、**パスワードで保護されたルーム**の参加端末同士が画像ファイルを交換できる HTML アプリ。

- 全部の画像本体を毎回配布するのは通信量が大きすぎるため、ルームごとの**コラージュサムネイルシート**（既定：横4 × 縦8 の集合画像）をクライアント側で自動生成し、ルーム全員で交換・表示する
- 画像**本体**は、サムネイルをクリックしたときだけ、データを持つクライアント（保持者）へリクエストして取得する（サーバーは中継のみ）
- **拡散許可**: 本体を取得・保存した参加者はその時点で保持者となり、他の参加者への転送応答に参加できる（§9.4）
- **重複排除**: サムネイルは部屋ごとに一意だが、画像本体はクライアント保存領域（OPFS）内で**SHA-256ハッシュによりグローバルに1個**だけ持つ（複数部屋で同一画像なら本体は共有、メタデータの部屋リストのみ増える）（§7）
- サーバー（Pico2 W / Kaluma または Node）の改変は不要。既存のチャット中継 (`cmd: 'C'`) をそのまま transport に使う

オフラインでも作動し、OPFS に保存済みの画像・メタデータ・サムネイルシートは、WS 切断状態でもルーム別のビュー（カレンダー表示）から参照できる。

### 1.1 ゴール

- 部屋作成者はパスワードを設定でき、そのパスワードを知らない端末はルームのデータにアクセスできない（アプリ層認証、§6）
- ルーム参加者は自分の画像コレクションのサムネイルを自動で全参加者に配布できる
- サムネイルクリック 1 回で本体画像を取得し、ブラウザ上で表示できる
- 表示画面で「保存」→ ローカル OPFS へ保存、「DL」→ OPFS 保存 + ブラウザダウンロードできる
- オフラインでも、OPFS 上の画像とサムネイル一覧を閲覧できる
- 部屋はタブで分割し、それぞれ独立した接続・表示状態を持つ
- サムネイル一覧は**カレンダー表示**（日/週/月切替）で、現在を基準に投稿時刻の降順で配置される
- **同期モード**では未所持の共有画像を順次自動取得する（ユーザー操作が優先、§9.9）
- 削除はゴミ箱による論理削除で、30日経過・ゴミ箱空/個別削除で物理削除（§9.8）
- 部屋の共有画像を 10MB 単位の ZIP 分割で一括ダウンロードできる（§9.10）
- OPFS の使用量をヘッダーに常時表示し、画像保持の変化ごとに更新（§9.11）
- 古いスマホ（最新版 Firefox でやっと動く程度）を一次ターゲットとし、レンダリング窓・単一転送などの低メモリ設計を守る（§3, §5.5, §8.6）

### 1.2 非ゴール

- サーバー側での画像永続化・認証（サーバーは中継のみ。認証はアプリ層で実装する。§3 制約参照）
- 通信の暗号化（HTTPS 非対応の LAN 前提。認証は共有確認 challenge-response で、盗聴耐性は限定的。§6.5）
- 音声・動画など画像以外のファイル形式（v1 は `image/*` のみ）
- 16KB 超 WebSocket フレーム・バイナリフレームの新設（既存 TEXT メッセージ機構のまま）

### 2.2 モジュール分割一覧（機能別 ESM・共用設計）

**設計規約**

- 命名: 新規ファイルは snake_case、named export / `export class` の ESM。bundler なしでブラウザが直接解決できる相対パス import のみ（import map は使わない）
- **依存方向**: `modules/*`（共用）は `modules/imgroom/*` を import しない。アプリ固有 → 共用・既存ユーティリティの一方向のみ。既存 `Y.js/Vw.js/const.js/file_util.js/OPFS.js` は位置を変えず、新規モジュールもここを import する
- 共用モジュールは**追加的変更のみ**（既存 export の削除・シグネチャ破壊禁止）。破壊的変更が必要なら別名ファイル（例 `p2p_file_v2.js`）で並存し、旧は当面残す
- 各ファイル冒頭に `@module` / `@version`（コメント管理のセマンティックバージョン）を記載

### 2.1 技術基盤（生JS/ESM・外部モジュール不使用）

- **生 JavaScript + ESM** を基本とする。フレームワーク・TypeScript・フロントエンド用 bundler は使わず、`wwwroot` 静的配信 + ブラウザのネイティブ ESM import で動作させる
- **実装は本プロジェクト内で完結させ、外部モジュールは読み込まない**（ネットワーク CDN 参照は禁止）。**例外は `wwwroot/modules/` に配置済みの 2 ファイルのみ**（いずれもリポジトリ内静的配信ファイルで、§6.4 の QR 生成/復号に使用。§2 ファイル構成）:
  - `modules/qrcode.es.min.js`: QR **生成**（davidshimjs "QRCode for Javascript library" の ESM ポート。`QRCode`/`HtmlQRCode`/`SvgQRCode`/`CanvasQRCode` を export、`correctLevel` 既定 H）
  - `modules/jsQR/jsQR.es.min.nosjis.js`: QR **復号**（cozmo jsQR の ESM 省サイズビルド。`export const jsQR`。引数 `(imageData, width, height, options?)` → `{data, binaryData, version, …}` または `null`）
  - jsQR の nosjis ビルドは**漢字モード（Shift-JIS）の直接解析を行わない**。ペイロードは BASE64URL（ASCII）のみを使用するため影響なし（§7.2 と整合。QR ペイロードに非 ASCII を載せないこと）
- 必要になるモジュールはプロジェクト内に新規実装する:
  - `modules/zip.js`: ZIP **書き出し**（圧縮方式 DEFLATE（method 8）⇄ STORE（method 0）をエントリごとにより小さい方で自動採用。DEFLATE はブラウザ標準 `CompressionStream('deflate-raw')` で生成し、CRC-32・ヘッダ組み立てのみ自作。ファイル名は UTF-8 + bit11（EFS）+ Info-ZIP Unicode Path extra field（§9.10）。実装見込み約 200 行）
- **不足モジュールの報告**: なし（QR 生成・復号は配置済み 2 モジュールで確保、v0.5）

- サーバー側（`TMiniWebServerES/`）の変更は**なし**。既存ルート `TMWS.withWS('/ws/chat/<roomId>')` を再利用する（roomId は BASE64URL 変換後の部屋名。§7.3）。
- デプロイ: `npm run wwwload`（wwwroot 直下を全ファイル loop で put するため新規ファイルも自動的に対象）。
- Node 開発サーバー: `npm run server` → `http://localhost:8080/img_room.html`

## 4. 用語

| 用語 | 定義 |
| --- | --- |
| 部屋（room） | 既存チャットの `<roomId>`。ユーザー入力名を BASE64URL 変換したものを roomId とする（§7.3） |
| 作成者 (creator) | 部屋を最初に作成したユーザー。部屋設定（seedSaltedHash・作成者 uid）の更新・パスワード再発行権限を持つ |
| seedSaltedHash (pwHash) | 平文パスワード由来の**シードソルトハッシュ** `Y.B2U(H.d(password + '|' + ridB64U + '|' + salt, HASH_ROUNDS))`（**v2.11 §38 で origin を除去**。旧式は `…|ridB64U|origin|salt…`。オリジン統制は §6.2 検証 2 が担う）。ソルトは不変データ（部屋名 rid・オリジン）+ 期間（通常/同期: UTC `YYYYMM`、サーバー: 参加日 `YYYYMMDD`、§6.7）。**ログイン成功時に OPFS の room.json へ保管**し、再参加時は平文パスワードの代わりに、採決時は自分の保管値で joiner を検証するのに使う（§6.2）。期間外は無効。平文パスワードは保存・通信しない |
| 本体 (body) | 共有対象の原画像バイナリ。**h10 をキーにクライアント内グローバルで 1 個** |
| h10 | 画像バイト列（メタデータを一切含まない純粋なバイナリ）の SHA-256 ハッシュ `Y.B2U(H.d(bytes, 10))`（[OPFS.js](../wwwroot/OPFS.js) `OPFS.x` と同一方式）。本体 ID・重複排除キー兼用 |
| メタデータ | 本体に紐づく付随情報（ファイル名・所属部屋リスト・投稿者・投稿時刻・MIME。§7.1）。h10 でインデックス |
| サムネイル | 本体からクライアント側で生成した縮小画像（既定 96px、正方形 center-crop）。**部屋ごとに一意**（同一画像でも部屋が違えば各自のサムネイル/シートに含まれる） |
| シート (sheet) | サムネイルを `GRID_COLS×GRID_ROWS`（既定 横4 × 縦8）のグリッドで合成した 1 枚のコラージュ JPEG。1 シート最大 32 コマ。**部屋 × 投稿者 単位**で ID 採番 |
| インベントリ manifest | 「このユーザーが、どの本体を、どの部屋のどのシートコマに保持しているか」の一覧（§7.4） |
| 保持者 (holder) | 本体を OPFS に保存している参加者。**拡散許可により取得者も保持者になれる**（§9.4） |
| タブ | アプリ画面上の部屋単位 UI。部屋ごとに独立した WS 接続・view 状態を持つ |
| ゴミ箱 | メタデータ `d` による論理削除状態。30日保持ビュー、復元/個別削除/空にする（§9.8） |
| ページ（カレンダー） | レンダリング窓管理の単位。月/週/日表示それぞれの表示期間1個分（§5.5） |
| 同期モード | 部屋の未所持画像を自動で順次取得するモード。通常モードとトグル切替（§9.9） |
| 許可オリジンリスト (oa) | 参加を許すページオリジンの一覧。`xorig` 有効時は部屋設定で管理、無効時は自オリジン 1 個に強制上書き（§6.6） |
| トランザクション処理者 | 設定/状態ファイルを排他ロックで直列読み書きする単一タブ（ロック保持者）。他タブは処理委譲する（§11.1） |

## 5. 画面構成（UI）

### 5.1 起動時の振り分け

- URL hash に部屋指定がある場合（`img_room.html#<roomNameB64U>`、QR 読み取りからも入力される）: **部屋ログイン画面**（ユーザー名 + パスワード入力欄、§5.2）
  - ログイン画面に**モード選択**（ラジオ/セグメント）: **通常 / 同期 / サーバー**（既定: 通常。サーバーモードは §5.7）。同期モードは通常⇄同期をヘッダートグルで後から切替可だが、**サーバーモードはログイン時の選択のみで、切替にはログアウトが必要**（§5.7）。未許可部屋（`srvOn=false`）では「サーバー」選択肢が disabled（§6.8）
  - その部屋が**自ブラウザプロファイルでログイン済み**の場合（§9.12）、ログインフォームは表示せず「ログイン済み（uid・モード）: セッションへ参加」表示となる（別 uid での再ログインはログアウト後に可能）
- 部屋指定がない場合: **ホーム画面** = 登録済み部屋のタブ一覧 + 「部屋作成」ボタン（§5.3）

### 5.2 部屋タブと部屋画面

- 上部に**タブバー**（部屋名 + 接続状態バッジ）。タブごとに以下を持つ。「＋」タブで新規接続（ログイン）または部屋作成
- アプリ共通**ヘッダー**（タブ切替と無関係に常時表示）:
  - **OPFS 使用量表示**: ローカル保持バイト数の合計（bodies + meta + sheet）を human readable 表示。画像保持の変化ごとに更新（§9.11）
  - **モード切替トグルスイッチ**: 通常モード ⇄ 同期モード（アクティブタブの部屋に適用、§9.9。サーバーモードでは非表示/無効で、解除にはログアウト要、§5.7）
  - **言語セレクト**（`auto`/日本語/English）: 変更で `LANG` 設定保存（store_tx 経由）+ 全 UI 即時再描画（§2.2 i18n）
  - **ゴミ箱アイコン**: ゴミ箱ビューを開く（§5.6）/ **一括 DL ボタン**: 部屋の画像を ZIP 一括ダウンロード（§9.10）
- 各部屋タブの内容:
  - 参加者バー（userId + 保持画像数。参加/退出のリアルタイム表示）
  - 共有部: ファイル選択（`FileUtil.oFL`）+ 選択画像プレビュー + 「共有」ボタン
  - **カレンダービュー**（§5.5）: サムネイルグリッドの代わりにカレンダー上へサムネイルを配置
  - **フッター（同期モード時のみ）**: 取得対象数と取得済み数の進捗表示（§9.9）
  - 状態バー: 接続状態（オンライン/オフライン）、転送進捗、トースト通知
- 「部屋設定」メニュー（ルームキーアイコン）: QR 表示/DL、パスワード再発行（作成者のみ）、許可オリジンリスト管理（作成者のみ・`xorig` 有効時、§6.6）、**サーバーモード許可 ON/OFF（作成者のみ・随時切替可、§6.8）**、退室、タブ閉じる

### 5.3 部屋作成画面（作成者のみ）

- 部屋名入力（ユーザー入力 → BASE64URL 化して roomId。同一 roomId の部屋が既に存在する場合は作成不可とし、ログイン画面へ誘導）
- パスワード設定:
  - 手入力 or **「自動生成」**ボタン → 512bit（64bytes）乱数を BASE64URL 化したパスワードを生成表示（§6.3）
- 作成完了後、自分の OPFS に部屋設定を保存し、自分が作成者（creator）としてルームに参加。他の端末には同じパスワード/QR を配布して参加させる
- 作成オプション: **クロスオリジン許可 `xorig`**（既定 false。true にすると作成後、部屋設定メニューで許可オリジンリストを管理、§6.6）
- 部屋作成・パスワード再発行 UI は**その部屋を作成したユーザー本人にのみ**表示される（§6.2）

### 5.4 本体ビューア（サムネイルクリックで開くモーダル）

- 本体画像フルサイズ表示（`URL.createObjectURL`）+ メタデータ表示（ファイル名・投稿者・投稿時刻・所属部屋一覧・MIME・ハッシュ先頭8桁）
- ボタン: **保存**（OPFS 保存）/ **DL**（OPFS 保存 + ブラウザダウンロード）/ **閉じる**
- 未取得の場合は取得転送が進み進捗バー表示。オフライン時未取得画像は閲覧不可（エラー表示）

### 5.5 カレンダービュー（サムネイル表示）

- サムネイルは投稿時刻ベースで**カレンダー上に現在を基準として降順**配置。トグルで**日 / 週 / 月**表示を切替（既定: 月）
  - 月: 月幅カレンダー。各日のセル内に当該日の投稿サムネイル（新しい順・セル内スクロール）
  - 週: 7 列の週幅ビュー（現在週を基準、以降の未来日は空白）
  - 日: 1 日の投稿を時系列降順の横列
- 現在より未来の投稿は表示しない（不正時刻は最終受信時刻で補正し警告）
- 実体はシートスライス画像（§9.2）で、各コマ = manifest エントリ（`sid` + `p`）→ メタデータの `ts` でカレンダー位置を決める。ユーザー別セクション分けはしない（投稿者はコマ hover/タップで表示）
- **仮想レンダリング（低スペック機種想定）**: レンダリングは時刻降順の**ページ単位窓**で行う。初期は現在位置から**3ページ**（`CAL_WINDOW_PAGES`）分をレンダリング。スクロールで窓端を跨ぐたびに前後へ1ページずつレンダリングを進め、**窓外ページの DOM 要素と objectURL は開放**（`<img>` 除去 + `URL.revokeObjectURL`）する。窓外から再入室したページは再レンダリング
  - ページ定義: 月表示なら 1 か月、週表示なら 1 週、日表示なら 1 日 = 1 ページ
- **取得インジケーター**: 本体取得が開始されたら、該当サムネイルの**下に** progress（chunk 到達率）を表示する。該当サムネイルがレンダリング窓内に表示されている場合は必ず見える位置に出す（§9.3）
- **グレースケール表示**: ある画像の保持者（manifest 上で当該 `h10` を持つ uid）が**全員現在ルーム不参加**（退出済み/未接続）の場合、そのサムネイルは CSS `filter: grayscale(1)` + バッジ「室に無し」で表示する。ローカル本体があればクリックで閲覧可、未取得なら取得不能（§12）

### 5.6 ゴミ箱ビュー

- ヘッダーのゴミ箱アイコンから開く。論理削除（メタデータ `d` 設定）中の画像を一覧表示（投稿時刻・削除時刻・投稿者・所属部屋）
- アイテム操作: **復元**（§9.8 の条件でカレンダーへ復帰）/ **削除**（**即時物理削除**）
- 上部操作: **ゴミ箱を空にする**（全アイテム即時物理削除）
- 30日経過アイテムはアプリ起動/部屋起動時に自動物理削除済みとなる（§9.8）

### 5.7 サーバーモード（ログイン画面で選択する常時同期ノード）

- **選択**: ログイン画面のモード選択で「サーバー」を選ぶ。ログイン後の画面で通常モード⇄サーバーモードの切替はできず、**変更するにはログアウト**する（§5.1）
- **自動同期モード**: サーバーモードでは同期モードが常に ON（§9.9 の自動取得が常時稼働。優先度・フッター進捗の扱いも §9.9 に準ずる）。起動時に room.json（uid + pwHash/pwSalt、有効期間の判定は §6.7）があれば**自動ログイン**して稼働を再開する（§9.12）。ただし部屋がサーバーモード未許可の場合は自動ログインしない（§6.8）
- **サーバーモード許可**: 参加は部屋設定 `srvOn=true` の部屋のみ可（作成者専権・随時 ON/OFF 可、§6.8）。参加中に OFF へ変わった場合はただちに強制ログアウトされる（§6.8）
- **自動ダウンロード（ON/OFF 可）**: ON にすると、manifest 同期で**新着が確認されるたびに**該当画像の本体を自動取得し、**DL 相当の確定動作**（bodies+meta 保存・DL 済みマーク、§9.6 に準拠）を行う。判定の二重実行防止として、**DL 済み h10 の台帳を専用 OPFS ファイル `rooms/<rid>/autodl.json` に記憶**し、取得前に必ず照合 — 登録済み h10 は**無視**（bodies から消えていても再取得しない）。**クリアボタン**（確認ダイアログ付き）で台帳を空にし、自動 DL を最初からやり直せる（全対象が再取得・再 DL される）
- **参加者一覧**: 現在参加者（オンライン）の一覧表示（uid・保持画像数・接続状態）
- **過去参加者一覧**: 過去にこの部屋へ参加した履歴のある uid を参照表示（OPFS `rooms/<rid>/history.json` に記録: uid・最終観測時刻・参加回数。離脱者グレースケール判定（§5.5）や保持者不在の把握にも利用）
- **OPFS データ量表示**: 画面内に OPFS 使用量を表示 — 全体合計（§9.11 の値）に加え、**この部屋の共有分**（当部屋の manifest が参照する bodies+meta+sheet の合計）の内訳を表示
- 共有 UI は通常モードと同じく利用可能（サーバーモードは「常時稼働する同期参加者」であり機能制限は持たない）

## 6. 認証（部屋パスワード）

### 6.1 基本方針

サーバーに認証機構がないため（§3）、**アプリ層のハッシュ採決方式**で実装する。平文パスワードの保持は参加者側で接続セッション中のメモリ上のみ（§6.6）、恒久保存と検証への使用は seedSaltedHash のみ（§6.2）。

- ローカル保存: `rooms/<rid>/room.json` = `{rid, nm: 部屋名b64url, pw: seedSaltedHash, pwSalt: "YYYYMM"|"YYYYMMDD", srvOn, cr: creatorUid, cg: 設定世代, xorig: 許可オリジン有効, oa: [b64url(origin)…]}`（OPFS。`pw` は `pwSalt` 期間内のみ有効、§6.7。競合時 `conflict: true` 追記、§6.9。`nm` はホームの部屋一覧表示に使用）
- **認証完了前の端末に対しては、アプリは全データフレーム（§8）の送出も受理（データ系）も行わない**。認証待ちの受信フレームは破棄

### 6.2 認証シークエンス（全メンバー確認 + オリジンハッシュ）

参加希望者は**オリジンハッシュをパスワード由来値の前後に付与**したハッシュを各メンバーへ送り、**既存メンバー全員から OK** を受けて初めてログイン成功とする。検証は各メンバーが**自分の OPFS に保管済みの seedSaltedHash**（§4、ログイン時に保存）で行うため、平文パスワードの保持は不要（自動再参加メンバーも採決できる）。

- 参加者側の値（`location.origin` = 自ページオリジン、`salt` は §6.7 の期間ソルト: 通常/同期=UTC `YYYYMM`、サーバー=参加日 `YYYYMMDD`）:
  - `ho = Y.B2U(H.d(location.origin, HASH_ROUNDS))`（**前**: オリジンのハッシュ値）
  - `hor = Y.B2U(H.d([...location.origin].reverse().join(''), HASH_ROUNDS))`（**後ろ**: 並び順を入れ替えたオリジンのハッシュ値）
  - `seed = Y.B2U(H.d(password + '|' + ridB64U + '|' + location.origin + '|' + salt, HASH_ROUNDS))`（seedSaltedHash。再参加時は room.json 保管値を**平文パスワードの代わり**に使用、§4）
  - `at = Y.B2U(H.d(ho + '|' + seed + '|' + hor + '|' + uid + '|' + salt + '|' + anonce, HASH_ROUNDS))`（`anonce` は参加希望者が生成する 16B b64url の試行 ID。平文パスワード・seed 自体は送信しない）

```mermaid
sequenceDiagram
  participant A as 参加希望 (PONTA)
  participant S as Server (Pico)
  participant B, C as 既存メンバー全員
  A->>S: WS open → {cmd:E} ENTER → {"ir":"W","uid","mode","salt","anonce","ho","hor","at"}
  S-->>B,C: W broadcast
  B-->>A: {"ir":"O","to":"PONTA","anonce","ok":true|false}（既存メンバー全員が採決）
  C-->>A: {"ir":"O","to":"PONTA","anonce","ok":true|false}
  Note over A: 既存メンバーの全員から ok=true → 認証完了 → J broadcast、M/S 交換開始
  Note over A: 1名でも ok=false → 「パスワードまたはオリジンが違います」
```

- **採決は既存メンバー全員**（自動再参加メンバーも含む）。各メンバーはログイン時に OPFS へ保存した自分の seedSaltedHash で joiner の `at` を再計算照合する。joiner と自分の `salt` が一致しない場合（期間ズレ）は一致し得ないため NOK
- メンバー側の検証（すべて成立で `ok:true`）:
  1. **salt 妥当性**: 通常/同期参加者は `salt` == 現在 UTC 月 `YYYYMM`。サーバー参加者は `salt` が `YYYYMMDD` 形式かつ参加当日以前、かつ部屋の `srvOn=true`（§6.8）。`mode=server` かつ `srvOn=false` は即不 OK
  2. **オリジン整合**: `oa`（許可オリジンリスト、§6.6）内のいずれかのオリジン o について `ho == H.d(o)` かつ `hor == H.d(reverse(o))` が一致（前后のハッシュが同一オリジン由来であることを要求）
  3. **パスワード整合**: `at` が**自分の room.json に保管した seedSaltedHash** による同一計算（uid/salt/anonce は joiner 値を使用）と一致
- 既存メンバーが 0 名の場合「メンバー不在のため認証できません」（オンライン既存メンバー 1 名以上が参加条件。作成直後の作成者参加は §5.3 の作成処理で設定を確立するため採決不要）。**OPFS に room.json を持つ端末が起動時に再認証を要求されるのは、ルームへ再接続する場合のみ**（単体オフライン利用は §9.7）
- 応答管理: `REQ_TIMEOUT` 以内に未応答の既存メンバーがいる場合 `W` を 1 回再送。なお未応答なら当該メンバーを**不 OK 扱い**（= ログイン失敗、再試行可）。メンバー側は処理済み `anonce` をセッション中保持し、同一 `anonce` の再採決要求には応答しない（§6.5）
- 作成者特権: `room.json` の `cr` と自 uid が一致する端末のみ「部屋作成（同一部屋の再作成ではない）」「パスワード再発行」UI を表示。`cr` の判定はローカル情報 + 作成者が broadcast する設定フレーム `C{rid,pw,cr,cg}` でメンバー間整合（§8.3）。**作成者本人が参加していない部屋の再発行は不可**

### 6.3 パスワード自動生成（512bit BASE64URL）

- `crypto.getRandomValues(new Uint8Array(64))` → `Y.u2B` → `Y.B2U` → **86 文字の BASE64URL 文字列**
- 生成値は入力欄にそのまま設定（コピー可能）、保存・通信はしない（QR 表示/DL は明示操作時のみ）
- 再発行: 作成者が再発行ボタン → 新パスワード生成 → 新 seedSaltedHash（現在期間 salt 付き）へ更新 → `C` フレーム broadcast（cg++）→ 全メンバー room.json 更新。**旧パスワードでの認証は以後不可**

### 6.4 QR 共有 / スキャン（生成: `qrcode.es.min.js` / 復号: `jsQR`）

- QR ペイロード（文字列）: `TMIWR1:<ridB64U>:<password>`（部屋指定とパスワードの一括共有。ASCII のみ・§2.1）
- **生成〜復号検証ループ（必須）**: 生成側モジュールの出力が、読み取り側（jsQR）で確実に復号できることを検証してから表示する:
  1. `text = ペイロード` で `CanvasQRCode`（既定 `QR_SIZE_PX = 256`、`QR_CORRECT_LEVEL = H`）を生成
  2. 生成 canvas の `getImageData()` を **jsQR**（`modules/jsQR/jsQR.es.min.nosjis.js`）に渡して復号し、`result.data` と `text` を比較
  3. `null`・不一致の場合は **`text` の末尾にスペース 1 文字を追加**（`text += ' '`）して再エンコードし 2 へ戻る。生成モジュールの型番自動選択が変わり、jsQR が読み取りやすいコードに収まる可能性が高い
  4. 復号成功したコードのみ表示・**PNG DL**（`toBlob('image/png')` + `<a download>`）。上限 `QR_VERIFY_RETRY = 8` 回で失敗時はエラー表示（文字列コピーは常に提供）
  - 検証で追加されたスペースはペイロードの一部として QR に載る。受信側は `TMIWR1:` 前方一致パースで末尾スペースを除去して扱う（形式上の互換性なし）
- 入力側（復号はすべて jsQR）:
  - ログイン画面/部屋作成画面に「QR スキャン」ボタン
  - **カメラスキャン**: `getUserMedia` + video frame の `getImageData` → jsQR。Secure Context 必須のため **LAN http 接続ではカメラスキャン不可**（ボタン押下時に説明表示）
  - **ファイルスキャン**: QR の PNG 画像ファイル選択 → canvas 経由で `getImageData` → jsQR（カメラ不要、非 Secure Context でも動作）
  - **最終フォールバック**: QR 表示時に併記されるペイロード文字列のコピーペースト入力
- スキャン結果の rid が既存タブの部屋と同一の場合、そのタブを開く

### 6.5 認証のセキュリティ水準（割り切り宣言）

- 認証により**平文パスワードと seedSaltedHash の単体再送はしない**（送るのは `ho`/`hor`/`salt`/`at` のみ）。LAN 上の盗聴者が成功時の `W`（`ho/hor/salt/at/anonce` セット）を捕捉すると、同一 salt 期間内（§6.7）に限り同一セットの再生で認証を模擬できる（`at` は seedSaltedHash 相当の秘密値の役割を持つ。対策としてメンバー側は処理済み `anonce` をセッション中に保持し重複 `W` を不 OK とする）。また seedSaltedHash は room.json に OPFS 保存される**部屋共有の期間秘密**であり、このファイル自体の漏洩は期間内の認証模擬を許す（敵対的脅威モデルは対象外）
- 目的は「パスワードを知らない参加者によるデータアクセス防止（LAN 内のお子様・部外者レベル）」であり、敵対的ネットワークの脅威モデルには対応しない

### 6.6 クロスオリジンホスティングと許可オリジンリスト

同一の HTML アプリが**別のオリジンにホスティングされ、同じ WebSocket サーバーを利用する**構成を許可するかどうかのオプションを持つ。

- 作成オプション: `xorig`（クロスオリジン許可 true/false、既定 false）。**単一オリジンにするかマルチにするかは作成者のみが決定でき、部屋作成後は変更できない**（変更 UI なし。メンバーは `xorig` が自己の記録と異なる `C` を無視して警告表示、§8.3）。`xorig=true` の場合に限り、許可オリジンリスト `oa` の追加/削除を作成者が部屋設定メニューで管理可能（変更は `C` の `cg++` で伝搬）
- **許可する場合（`xorig=true`）**: 部屋は**許可オリジンリスト `oa`**（§7.2 により各オリジン文字列を BASE64URL 化して保持）を持ち、`C` フレームで全メンバーに伝搬・room.json に永続化する。認証（§6.2）は `ho`/`hor` が oa 内の同一オリジンと一致することを要求するため、リスト外のオリジンからの参加は全メンバー不 OK となる
- **許可しない場合（`xorig=false`）**: 各メンバーは oa を**自己の現在オリジン 1 個のみ**とみなし、`C` の oa 値を**強制的に上書き**して扱う（`oa=[現在のオリジン]`）。異なるオリジンから配信された同じ HTML からの参加はオリジン整合チェックで必ず不 OK → ログイン失敗
- **認証成功後の保持**: 参加者は「パスワード（平文は接続セッション中のメモリ上のみ）」と「許可オリジンリスト（`xorig`/`oa`）」と「seedSaltedHash」を持つ（room.json に永続化されるのは seedSaltedHash/pwSalt と oa/xorig/srvOn）
- 注意（§6.5 の水準で割り切り）: オリジンの主張はアプリ層のハッシュ自己申告であり、WS サーバーは Origin 検証に関与しない（サーバーに Origin 情報はない）。同一オリジン強制の本質的な目的は「別オリジン配布版による部屋への混入防止」

### 6.7 seedSaltedHash の期間ソルトと強制ログアウト

seedSaltedHash は期間ソルト付きで、**有効期限**を持つ（§4 計算式）。

- **通常/同期モード**: `salt = 現在 UTC 月の "YYYYMM"`。**UTC で月が変わった時点で強制ログアウト**（セッション側で UTC 月変化を検知するタイマ。所有者タブが検知 → §9.12 に従いプロファイル全体でログアウト）。以後の参加・再参加は**パスワードの再入力が必要**（room.json の `pw`/`pwSalt` が過去月なら自動再参加不可、§9.12）。再ログイン成功時に新しい salt の seedSaltedHash を room.json へ**更新保存**する
- **サーバーモード**: 月境界の強制ログアウト**免除**。`salt = サーバーモードで参加した日の "YYYYMMDD"`（参加時に確定し room.json の `pwSalt` に保存）。ブラウザ再起動等の再参加時は保存済みの `pw`（seedSaltedHash）+ `pwSalt`（参加日）で再参加する（§9.12）。ただし §6.8 の `srvOn=false` 時は強制ログアウト対象
- **採決・検証**: メンバーは joiner の `salt` に対し、**自分の OPFS 保管 seedSaltedHash** で `at` を再計算照合する（§6.2）。salt が期間外だと参加者・採決者双方の値が一致しないため、期間切れは自動的に認証不能となる（平文パスワードの保持資格制限は無い、v1.0）
- 全メンバーの room.json 保管値も月が変われば旧 salt となるため、**月境界では全員が強制ログアウト→パスワード再入力**という運用が強制される（サーバーモードのみ免除）
- ソルトの判定は常に現在 UTC 時刻から機械的に行う（設定項目ではない）。`xorig` と違い期間ソルト方式の変更は部屋設定に含めない

### 6.8 サーバーモード許可（`srvOn`、作成者専権・随時切替）

- **サーバーモードへの参加可否は部屋作成者の専権**。部屋設定 `srvOn`（true/false、既定 **false**）で管理する。ON/OFF は**途中で随時切替可能**（作成者のみ、§5.2「部屋設定」メニュー）。変更は `C` に `srvOn` を載せ `cg++` で伝搬・room.json に永続化（v0.8 の `xorig` が作成後変更不可なのと対照的）
- **サーバーモードでの参加中に `srvOn` が false になった場合**: 当該サーバーモード参加者は**ただちに強制ログアウト**（`C` 受信時に `mode=server` かつ `srvOn=false` を検知 → WS を閉じ「サーバーモードは作成者により停止されました」表示。§9.12 に従いプロファイル全体でログアウト、以後 `srvOn` が true に戻るまで自動再参加しない）
- `srvOn=false` の部屋のログイン画面では「サーバー」選択肢を disabled 表示（サーバーモード参加の `W` は採決で即不 OK、§6.2）
- 通常/同期モードは `srvOn` の影響を受けない

### 6.9 作成者の引継ぎと部屋再作成の競合（作成者端末消失時）

- 作成者端末がクリア/消失した場合の復帰手順: **同一部屋名で新しい管理者が部屋を作成し直し**（部屋名同一 → 同一 rid → 同一 WS 配信）、**新しい作成者がパスワードを再発行**する。再作成後は設定（`cr`/`cg`/seedSaltedHash）がすべて新であり、旧参加者はログインせず同席しない（v1 運用）
- **競合判定（後発ログイン）**: 旧作成者を含む旧部屋の参加者が後からログインを試みた場合、既存（新）メンバーの採決で必ず不成立となる。判定規則:
  - **先にログイン済みが勝ち**。ログイン側は不成立 = 強制ログアウト扱い（セッションを維持できない）。新旧の立場が入れ替わっても同様（後発側が常に不成立）
  - ログイン側が旧作成者（room.json の `cr` == 自 uid）で、受信 `C` の `cr`/`cg` がローカル記録と異なり、採決が全メンバー NOK の場合、メッセージ「**別の管理者が部屋を立ち上げているようです**」を表示
  - ローカル room.json に `conflict: true` を記し、以後の自動再参加を禁止（QR 再読込/パスワード再入力による再登録が必要）
- **参加中の再作成検知**: セッション中に `cr`/seedSaltedHash の異なる `C` を受信した既存メンバーは**強制ログアウト**（「部屋設定が再作成されました。再認証が必要です」）。設定の正当性は**先にログイン済みセッション側**が保持（新側は再ログインに採決が必要）
- データ本体（h10 bodies/meta・ゴミ箱）は部屋再作成の影響を受けずローカルに保持され続ける。失効するのは部屋への参加資格と設定のみ

## 7. データモデル

### 7.1 メタデータ（1 本体 1 個、部屋横断で共有）

```json
{ "h": "<h10>", "n": "<ファイル名 b64url>", "r": ["<ridB64U>", "<ridB64U2>"],
  "u": "<投稿者 uid b64url>", "ts": 1730983857000, "t": "<MIME>", "l": 1234567, "s": 890123,
  "d": null }
```

- `h`: **メタデータを一切含まない**画像生バイト列の SHA-256 ハッシュ（§4）
- `r`: 所属部屋の BASE64URL 配列。**複数の部屋でサムネイルに含まれる場合、この部屋名が増えていく**（§9.5）
- `u`: 最初の投稿者（作成者）。拡散で保持者が増える（§9.4）
- `ts`: 投稿時刻（初回投稿時の `Date.now()`、単位 ms）
- `l` / `s`: 原画像バイト長 / gzip 後バイト長（後者は chunk 数計算用）
- `d`: **ゴミ箱タイムスタンプ**。`null` = 通常、非 `null` = ゴミ箱（論理削除、§9.8）

### 7.2 BASE64URL 規則（ユーザー入力由来データ）

ファイル名・部屋名・uid などユーザー入力由来の文字列は、保存・通信ともに **UTF-8 → `Y.u2B` → base64url（`Y.B2U`）** で保持し、JSON 内の特殊文字・パス衝突・Kaluma/WS 実装の非 ASCII 問題を回避する（Y.js の B2U/u2U を使用）。復元時は U2b→UTF-8 デコード。

### 7.3 roomId

`rid = Y.B2U(H.d(部屋名, 4) 先頭16文字 + '-' + Y.B2U(部屋名b64url 先頭16文字))` とし、チャット URL の roomId パス成分に安全な文字列集合（`[A-Za-z0-9_-]`）に収める。QR には元の b64url 部屋名を載せ、受信側で rid を再計算する。

### 7.4 インベントリ manifest フレーム

```json
{"ir":"M","uid":"PONKO","gen":3,
 "sheets":[{"id":"roomA.PONKO.0","h":"<シートh10>","n":32}],
 "m":[{ "h":"<h10>","n":"…b64u","r":["roomA"],"u":"…b64u","ts":1730983857000,
        "t":"image/jpeg","l":1234567,"s":890123,"c":109,
        "sid":"roomA.PONKO.0","p":7 }, … ]}
```

- uid ごとの**全保持画像**（自投稿 + 取得保存済み）が対象 = 拡散の基礎（§9.4）
- `sheets[].id` = `<rid>.<uid>.<sheetIdx>`（部屋 × 投稿者 × 連番）。`sid` の p は行優先（`x=p%GRID_COLS, y=floor(p/GRID_COLS)`）
- 1 フレーム最大 64 エントリ、超過は同一 gen でページ分割連投（16KB 対策）

### 7.5 重複排除の原則

- 本体は `h10` が同一なら**グローバルに 1 個**（§10 の `bodies/<h10>`）。同一画像を複数部屋で共有/取得しても本体ファイルは増えず、メタデータ `r` に部屋が増える
- シートは部屋 × 投稿者単位で別ファイル（同一画像でも部屋別にサムネイルが分かれる）

## 8. 通信プロトコル

### 8.1 トランスポート（変更なし）

- 接続: `WebSocket → /ws/chat/<rid>`
- 送信エンベロープ: `{"cmd":"C"|"E"|"L","userId":"...","msg":"<フレーム文字列>"}`（`cmds` は [const.js](../wwwroot/const.js) と同一）
- 受信エンベロープ: `{"userId","msg","t"}`（サーバー broadcast。送信者自身にも届く）

### 8.2 フレーム種別

**(a) 制御フレーム** — JSON オブジェクト、`ir` フィールド必須。

| ir | 名称 | 宛先 | payload 例 |
| --- | --- | --- | --- |
| `W` | 参加要求（認証前可） | 全体 | `{"ir":"W","uid":"PONTA","mode":"normal|sync|server","salt":"YYYYMM|YYYYMMDD","anonce":"…","ho":"…","hor":"…","at":"…"}`（§6.2, §6.7） |
| `O` | 認証採決 | `to` 宛先 | `{"ir":"O","to":"PONTA","anonce":"…","ok":true}`（既存メンバー全員が応答、§6.2） |
| `C` | 部屋設定通知 | 全体 | `{"ir":"C","rid":"roomA","pw":"<seedSaltedHash>","cr":"PONTA","cg":2,"xorig":true,"oa":["aHR0cDovL2xvY2FsaG9zdDo4MDgw","…"],"srvOn":true}` |
| `J` | 参加告知（認証後） | 全体 | `{"ir":"J","uid":"PONTA","gen":3,"grid":[4,8]}` |
| `B` | 退出告知 | 全体 | `{"ir":"B","uid":"PONTA"}` |
| `M` | インベントリ manifest | 全体 | §7.4 |
| `S` | シート転送開始ヘッダ | 全体 | `{"ir":"S","uid":"PONKO","sid":"roomA.PONKO.0","h":"<シートh10>","t":"image/jpeg","l":45678,"s":40010,"c":5}` |
| `T` | シート取得要求 | `to` 宛先 | `{"ir":"T","to":"PONKO","sid":"roomA.PONKO.0"}` |
| `Q` | 本体取得要求 | `to` 宛先 | `{"ir":"Q","to":"PONKO","h":"<h10>"}` |
| `H` | 本体転送開始ヘッダ | `to` 宛先 | `{"ir":"H","uid":"PONKO","h":"<h10>","n":"…b64u","t":"image/jpeg","l":1234567,"s":890123,"c":109}` |
| `A` | 応答ステータス | `to` 宛先 | `{"ir":"A","to":"PONJI","h":"<h10>","st":"ok"\|"nf"\|"busy"}` |
| `G` | chunk 再送要求 | `to` 宛先 | `{"ir":"G","to":"PONKO","h":"<h10>","miss":[12,40]}` |
| `X` | 画像削除通知 | 全体 | `{"ir":"X","h":"<h10>"}`（投稿者の削除操作。受信側もゴミ箱へ論理削除、§9.8） |

- 「`to` 宛先」も中継上は broadcast のため、`to` が自分以外なら受信側で無視
- **認証前に受理する ir は `W/O/C` のみ**。認証後にデータ系 ir を有効化（§6.1）
- 「認証前に送出してよい ir は `W`（と採決応答の `O`）」

**(b) チャンクフレーム** — 短い文字列（JSON 化しない）。

```
~<h10>.<i>.<c>.<r>
```

- `~` = ImageRoom チャンク識別接頭辞（ws_chat2 の `h.i.c.r` との混同回避）
- `h10` = 転送対象（本体 or シート）のコンテンツハッシュ
- `i` = chunk index（0 始まり）, `c` = chunk 総数, `r` = base64url データ
- 生成: 元バイト列 → gzip（`Y.c`）→ `CHUNK_RAW=8192` バイトスライス（`Y.as`）→ base64url（`Y.u2U`）。既存 ws_chat2 と同一機構

### 8.3 部屋設定の整合

作成者は参加認証完了後、`C` を broadcast。メンバーは `cg` が新しいもののみ room.json へ反映（seedSaltedHash 更新＝再発行の伝搬）。`C` を受理した非作成者側は再発行できないことを UI で示す。

### 8.4 メッセージサイズ計算（16KB 上限対策）

```
msg  = "~" + h10(43) + ".i.c."(≒10) + r
r    = ceil(8192 * 4/3) = 10923
msg  ≒ 11.0 KB
+ {"cmd":"C","userId":"<≤64>","msg":...}  ≒  +100 B
合計 ≒ 11.1 KB < 16384  ✔
```

`M` は 64 エントリ/フレーム上限でページ分割（§7.4）。

### 8.5 受信フレーム判別（ws_chat2 互換維持のため順序固定）

1. `"~"` 始まり → 自アプリ chunk（既知転送でなければ破棄）
2. JSON パース可 かつ `ir` あり → §8.2 に従い認証状態別に受理/破棄
3. その他 → 無視

### 8.6 送信タイミング・同時実行数・ウォッチドッグ

- chunk 間隔: `CHUNK_GAP_MS = 100ms`（ws_chat2 の `wt` と同值、Pico 送信バッファ保護）
- 同時実行数: **取得（受信）は常に 1 ファイルずつ**（`IN_TRANSFERS = 1`）。他端末への応答（送信）は最大 `OUT_TRANSFERS = 2`、超過分はキューし `busy` 応答
- **新規画像のサムネイル交換スロットル**: 新規画像に伴う `M` broadcast（および後続のシート交換）は**最低 30 秒間隔**（`SHEET_BCAST_MIN_MS = 30000`）を開け、さらに各 broadcast 送信時に**最大 10 秒程度のランダム遅延**（`SHEET_JITTER_MS`）を追加する（参加者間の同時刻衝突防止）
- **転送ウォッチドッグ**: 転送中（取得・応答双方）、同一転送相手から `STALL_MS = 10000ms` 以上フレームが届かない場合（参加者が通信不能）、そのリクエストは**破棄**し、キューに再登録して別保持者候補でやり直す（§9.3）
- 優先度: **ユーザー操作（クリック取得・閲覧・一括DL）は同期モードの自動取得に常に優先**する（§9.9）

## 9. 主要フロー

### 9.1 共有（画像投稿）

1. ファイル選択（`image/*` 限定、`MAX_IMG_BYTES` 超過は拒否）→ 「共有」（現在アクティブな部屋タブに対して実行）
2. メタデータ生成: `h10` 計算、`n`（b64url）、`u`（b64url）、`ts=Date.now()`、`t`、`l`、`s`、`r=[現在rid]`
3. 本体を `bodies/<h10>` へ保存（ハッシュ重複排除のため既存ならスキップ、`r` マージのみ）
4. 当該部屋のシート再生成（§9.2 変更シートのみに影響）→ manifest `gen++` → `M` broadcast（**スロットル適用: 30s 間隔 + ≤10s ランダム遅延、§8.6**。差分取得は受取側の `T` 要求で実施）
5. 他参加者は manifest 差分から新シートのみ自動取得、カレンダーへ即時反映

### 9.2 シート生成とスライス表示（自動交換）

1. 画像追加時、原画像からサムネイル化（`THUMB_PX=96` 正方形 center-crop）
2. **部屋 × 投稿者**の画像リスト（投稿時刻降順）を 32 枚ずつシートへ分割。`GRID_COLS×THUMB_PX` × `GRID_ROWS×THUMB_PX` の Canvas にグリッド描画 → JPEG（q 既定 0.72）→ h10 → OPFS `rooms/<rid>/sheet/<uid>_<idx>.<h10>`
3. 変更のあったシートのみ再配布。シート未所持の受取側は `M` 受信時に `T` 要求 → `S` + chunk → gunzip → h10 検証 → OPFS 保存
4. 表示は Canvas で 32 コマへスライス（`drawImage(sheetCanvas, sx, sy, TW, TH, …)` + `toBlob` → objectURL）し、各コマを独立 `<img>` としてカレンダーへ配置。クリックハンドラが本体取得フロー起動

### 9.3 本体取得（サムネイルクリック）

1. 対象 `h10` が `bodies/` にあれば即表示（転送なし）
2. なければ manifest から保持者候補（`m` 内で当該 h10 を持つ uid、複数可）を選び `Q{to}`。**同一ファイルを複数保持者が持つ場合、保持者はファイル（h10）ごとにラウンドロビンで切り替え**、特定の参加者へ取得が集中しないようにする。応答なし/nf は次候補へ（§12）
3. 保持者: `bodies/<h10>` 読込 → `A{st:ok}` + `H` + `~` chunks
4. 受信: chunk 揃うか `G` 再送要求（上限 2 回）→ gunzip（`Y.d`）→ **h10 再計算一致検証**（不一致は破棄）→ objectURL 表示。この時点ではメモリ上のみ
5. **取得中は当該サムネイルの下のインジケーター**（chunk 到達率 progress）を、そのサムネイルがレンダリング窓内に表示されていれば必ず表示する。窓外の場合は再入室時に現在の進捗を再描画する
6. **保持者が 10 秒以上通信不能**（フレーム途絶）になった場合、ウォッチドッグが転送を破棄し、ラウンドロビンで別候補へ再リクエストする（§8.6）
7. 取得は常に 1 ファイルずつ（`IN_TRANSFERS = 1`）。他の取得要求は FIFO キュー（ユーザー操作由来が優先、§9.9）

### 9.4 拡散（保持者拡大）

- 本体を取得し「保存」した参加者は、自分の manifest（`M`）へ当該エントリを追加（`gen++`）→ broadcast → **以降その端末も保持者として `Q` に応答可能**
- 未保存の取得（ビューア表示のみ）は保持者にしない
- `Q` の候補選択はファイル（h10）ごとの**ラウンドロビン**（nf で除外、次候補へ `REQ_TIMEOUT` ごと。§9.3）

### 9.5 複数部屋への同一画像

- 部屋 A の画像を部屋 B でも「共有」（同一本体）: `bodies/<h10>` は既存、メタデータ `r` に `ridB` を追加、B の投稿者用シートにサムネイル追加、B の `M` で通知
- B のメンバーで既に A 経由で保持している端末は本体取得不要（`bodies` ヒット）、`r` マージのみ
- `X`（削除通知）は投稿者本人（`u`）のみ broadcast 可。受信側はゴミ箱へ論理削除（§9.8）

### 9.6 保存 / ダウンロード

- **保存**: 表示中の本体を `bodies/<h10>` へ書き込み + メタデータ保存 + 拡散 manifest 更新（§9.4）
- **DL**: 保存（済みならスキップ）後、`URL.createObjectURL(new Blob([ab,{type:t}]))` + `<a download=n（デコード後の実ファイル名）>`

### 9.7 オフライン動作

- WS `close`/`error` 検知でタブにオフラインバッジ。転送中の転送は中断・キューへ戻す
- カレンダービューは OPFS の `manifest.<uid>.json`（uid 毎の最終受信 manifest）+ メタデータ + `sheet/*` から全参加者分を再構築
- クリック時: 本体があれば表示 + 保存/DL 可、無ければ「オフラインでは取得できません」
- 再接続時: 認証（room.json の seedSaltedHash で §6.2 の採決参加）→ `J`（gen++）→ 差分同期

### 9.12 プロファイル単一セッション（部屋単位のログイン制御）

- **部屋単位のログイン/ログアウトはブラウザプロファイル単位で 1 個**に制御する（タブ数に関わらず、同一部屋の WS セッション + uid はプロファイルに 1 つ）
- **セッション所有者タブ**: 最初にログインしたタブが所有者となり WS 接続を保持する。所有者権は §11.1 と同一機構（`room.<rid>` 単位の排他ロック + ハートビート、BroadcastChannel `imgroom.session.<rid>`）で担保
- **ミラータブ**: WS を開かず、所有者が配信する状態スナップショット（参加者表・manifest・転送進捗・sync 進捗）で描画し、操作（共有/削除/取得/モード切替）は所有者へ委譲（§11.1 の tx 委譲と同形）
- **ログイン重複防止**: プロファイル内でログイン中の部屋を開くと、ログインフォームでなく「ログイン済み: セッションへ参加」表示（§5.1）。**別 uid でのログインはログアウト後**に可能
- **ログアウト**: いずれかのタブで実行するとプロファイル全体でログアウト（所有者が WS を閉じ、全ミラータブが未接続表示。`roomLogin.<rid>` を null 化）
- **所有者タブ閉鎖**: ハートビート失効（§11.1 に準拠）→ ミラータブの 1 つがセッション権を取得し、room.json の uid+seedSaltedHash で**同一 uid 自動再参加**（パスワード再入力不要。ただし `pwSalt` が有効期間内であること — 通常/同期は同 UTC 月、サーバーは参加日ソルト、§6.7。期間切れはパスワード再入力へ）。全タブ終了でセッション消滅、再表示時はログイン済みのため同様に自動再参加
- **月境界**: UTC 月変化で通常/同期セッションは失効（§6.7）→ 全タブにログアウト波及、`roomLogin.<rid>` を null 化。以後はパスワード入力でのみ再ログイン可
- 参加履歴: セッションイベント（認証成功/`J`/`B`）で `rooms/<rid>/history.json`（uid・最終観測・参加回数）を更新（§5.7 の過去参加者一覧・§5.5 の判定で参照）

### 9.8 ゴミ箱と削除（論理削除 → 期限で物理削除）

- 削除操作（ビューアの「削除」/ 投稿者の「取り下げ」）はメタデータ `d = 削除時刻` の**論理削除**。実データ（bodies/meta/sheet）はそのまま
  - カレンダービュー・manifest（`M`）・同期モード対象から除外。ゴミ箱ビュー（§5.6）に表示
  - 投稿者（`u` 本人）の削除時は `X` を broadcast → 受信参加者も同様に `d` 設定（論理削除）
- **物理削除**（bodies + meta + sheet の実 OPFS 削除）の発動条件:
  1. **ゴミ箱で個別「削除」** → 即時物理削除
  2. **「ゴミ箱を空にする」** → 全ゴミアイテム即時物理削除
  3. **`TRASH_KEEP_DAYS = 30 日` 経過** → アプリ/部屋起動時にスイープ（`now - d > 30日`）
- bodies はグローバル共有（§7.5）のため、物理削除は**他の部屋の meta / ゴミ箱（論理削除中含む）から参照が切れてから**実行する（参照カウント的に meta を走査）
- **復元**は投稿者本人のみ可（`d = null` へ戻し `M` 再 broadcast）。他参加者のコピーは投稿者の再共有まで復元しない

### 9.9 同期モード（自動取得）

- ヘッダーのトグルスイッチで**部屋タブごと**に通常モード ⇄ 同期モードを切替（状態は `app_state.json` の `MODE.<rid>` に永続化、§11。書き込みは store_tx 経由。**サーバーモードの部屋ではトグル無効**、§5.7）
- 同期モードでは、参加者 manifest を走査し**自分が持っていない画像**（`bodies/` 不在かつゴミ箱 `d` 以外）を**順次自動取得**する
  - 順序: 投稿時刻の降順（新しい順）
  - **優先度: ユーザー操作（クリック取得・閲覧・一括DL）が常に優先**。操作転送の完了まで自動取得は中断・待機し、空闲になると再開する
  - 取得は常に 1 ファイルずつ（§8.6）
  - **取得対象が途中で消えた場合**（`X` 削除通知 / 保持者が全員退出 / h10 検証失敗）→ **当該取得は破棄**（キューから除く。同一セッションで再試行しない）
  - **ゴミ箱対象の除外**: **ローカル端末のゴミ箱に入った**（meta `d` 設定済み）画像が新たな同期対象になった場合、当該端末では**無視**する（§9.9 キュー・§5.7 自動 DL ともにスキップ。自動 DL 台帳に h10 が無くても取得しない）。ゴミ箱アイテムが**物理削除/期限スイープでゴミ箱から消えた**後は、通常の対象として再び同期される（再取得・再 DL される）。ゴミ箱から復元した場合はローカル所持となるため対象外
- **フッター表示**（同期モード中）: `取得済み n / 取得対象 m`（m はモード開始時点の未所持数。manifest 更新で再計算）。完了時「同期完了」表示
- 自動取得で取得した画像は**OPFS へ保存済みとして扱う**（保存ボタン不要、拡散 §9.4 で保持者になる。v0.4 で確定）

### 9.10 部屋の ZIP 一括ダウンロード

- ヘッダーの「一括 DL」ボタンで、**現部屋で共有対象としている OPFS 上の画像**（現部屋 manifest に載るエントリ、ゴミ箱除く）を一括ダウンロードする
- **10MB（`ZIP_CHUNK_MB`）単位で ZIP に分割**し、順次ダウンロード（古いスマホ対策: ArrayBuffer を単一積層せず、エントリごとの Blob parts を逐次連結して ZIP 化、§13）
- 圧縮: エントリごとに **DEFLATE（method 8、`CompressionStream('deflate-raw')`）** と STORE（method 0）を試し**小さい方**を採用（CRC-32・サイズは両方式分を保持）。API 非対応環境は STORE にフォールバック
- ファイル名（日本語等非 ASCII を許容）: ローカルヘッダ・セントラルディレクトリとも**名前は UTF-8 で格納**し、**汎用フラグ bit11（UTF-8/EFS）をセット**、加えて **Info-ZIP Unicode Path extra field（0x7075）** を付与する。これで Win10+/macOS 標準展開で文字化けしない（§17: NFC/NFD 正規化差は名前の Byte 列差として残るが文字化けではない。XP 等超旧ツールは非保証）
- ZIP 内エントリ名はメタデータ `n` デコード後の実ファイル名（重複時 `_<h10先頭8>` サフィックス）
- ZIP64 は使用しない（1 ZIP ≪ 4GB・エントリ少数で 32bit フィールドで十分）
- ZIP ファイル名: **`<BASE64URL の部屋名> + <DL開始時刻 yyyyMMddhhmmss> + <連番>.zip`**
  - 例: `cm9vbTEtQUJjRDEyMzQtYWJj-20261108023803-001.zip`（連番は 001〜、3 桁ゼロ埋め）

### 9.11 OPFS 使用量集計（ヘッダー表示）

- ローカル画像が更新されるたび（共有/保存/削除/物理削除/ゴミ箱操作/シート再生成）に、`bodies/` + `meta/` + 全部屋 `sheet/` の合計バイト数を `OPFS.ls` 再帰で集計し、ヘッダーに human readable 表示（例 `使用量: 12.3MB`）
- 補足表示として `navigator.storage.estimate()`（ブラウザ視点の quota/usage）を併記可
- 集計コスト対策: 変更イベントのデバウンス（最短 2s 間隔）で実行。起動時・ゴミ箱表示時にも更新

## 10. OPFS ストレージ構成

`OPFS.i('imgroom')` の管理ハッシュルートディレクトリ下:

```
<hashed root>/
├─ user_settings.json                   # ユーザー設定（§11 の設定値。store_tx 経由でのみ読み書き）
├─ app_state.json                       # アプリ状態（同期モード状態・前回ゴミ箱スイープ刻印等。store_tx 経由）
├─ rooms/<rid>/room.json                # {rid, pw:seedSaltedHash, pwSalt, srvOn, cr, cg, xorig, oa[, conflict]}（参加した全端末が保持）
├─ rooms/<rid>/manifest.<uid>.json      # 参加者uid毎の最終manifest
├─ rooms/<rid>/history.json             # 参加履歴（uid・最終観測・参加回数、§5.7/§9.12）
├─ rooms/<rid>/autodl.json              # サーバーモード自動DL済み h10 台帳（§5.7。クリアボタンで空に可）
├─ rooms/<rid>/sheet/<uid>_<idx>.<h10>  # サムネイルシート（部屋×投稿者単位）
├─ bodies/<h10>                         # 画像本体（ハッシュキー、グローバル一意・部屋横断共有）
├─ meta/<h10>.json                      # メタデータ（§7.1、1本体1個、ゴミ箱状態 d を含む）
```

- 読み書きは `OPFS.x` / `OPFS.y` / `OPFS.rmh` / `OPFS.ls` / `OPFS.w` / `OPFS.r` を利用（パスに `/` を含む `n` で階層自動作成）
- 初期化: `await OPFS.rd` 完了前提（OPFS.js の rd 規約）
- ガベージコレクション: 全 manifest と `meta` の参照外の `sheet`/`bodies` はルーム起動時に掃除（間隔は §17）

### 11.1 タブ間トランザクション（単一処理者・直列アクセス）

同一ブラウザの**複数タブが同じ部屋に参加**している場合、設定/状態ファイルの同時読み書きで更新が消失しうるため、`store_tx.js` により**特定の 1 タブ（処理者）のみが処理するトランザクション機構**を構成し、シリアルアクセスとする。

- API: `StoreTX.tx(name, fn)` — `name` はファイル識別名（`user_settings`/`app_state`）。`fn` は read-modify-write 関数で、ロック内でのみ実行される
- **単一処理者**: `navigator.locks.request(name)`（Web Locks API）の排他ロックを保持したタブが処理者を兼ねる。他タブからの `tx` 要求は BroadcastChannel（`imgroom.tx.<name>`）で処理者へ委譲され、結果と変更スナップショットを受け取る（他タブのキャッシュは通知で無効化）
- **代替手段**: Web Locks 非対応ブラウザ（古い Firefox 想定）では、**BroadcastChannel ハートビートによる処理者選出**（2s 間隔で `leader:<name>` を宣言、6s 応答が途絶えたタブが最小タブ ID 順で引き取り、OPFS へロックトークンファイル `<hashed root>/locks/<name>.lock` を記述して状態可視化）。BC は全対応済みのため追加モジュール不要
- ロック保持タブが閉じられた場合: ハートビート停止 → 他タブが規定時間後にロックを取得し次処理者となる（待機中の委譲要求は再送）
- 同一タブ内の `tx` は FIFO キューで直列化（ロック再取得は不要）
- 同一機構は部屋セッション単位にも適用される（`room.<rid>` ロックによる単一所有者タブ、§9.12）

## 12. エラー処理

| 事象 | 動作 |
| --- | --- |
| 認証失敗（いずれかの `O{ok:false}`） | 「パスワードまたはオリジンが違います」表示、タブは認証待ちのまま（§6.2） |
| 採決応答なし（`REQ_TIMEOUT` → `W` 再送後も） | 未応答の既存メンバーを不 OK 扱い → 「認証できません（採決応答なし）」再試行ボタン（本体閲覧等のオフライン機能は継続可） |
| 許可外オリジンからの参加 | オリジン整合チェックで全メンバー不 OK → ログイン不可（§6.6） |
| chunk 欠落（`c` 経過で一部欠け） | `G{miss}` 再送要求 → 上限超過で転送失敗、UI エラー |
| h10 検証不一致 | 受信データ破棄、エラー toast（再試行不可） |
| `A{st:nf}` / `Q` 応答なし | 保持者候補を順に試行（最大 3 候補）→ 全滅で「保持者が見つかりません」 |
| `A{st:busy}` | `REQ_TIMEOUT` 後に再 `Q`（最大 2 回） |
| WS 切断 | オフラインモード（§9.7）。転送中の転送は中断・キューへ戻す |
| OPFS 不存在環境 | 起動時に `navigator.storage.getDirectory` 失敗 → 共有・保存・認証永続化が無効（警告表示、接続中のセッション中のみシート交換可の縮退） |
| 同一 userId 衝突 | `J`/`W` の uid 一致検知時、自 uid を自動リネーム（`uid-2`…）して再接続。room.json の `cr` 一致は uid 依存のため衝突時は作成者権限判定を再確認（§6.2 注意） |
| 不正時刻（未来 ts） | 最終受信時刻で補正 + 警告ログ |
| 取得相手が 10 秒以上通信不能 | ウォッチドッグ（§8.6）が転送を破棄 → ラウンドロビンで次候補へ再リクエスト |
| 同期対象の消滅（`X`/保持者全員退出/検証失敗） | 当該取得をキューから除き破棄（同一セッションで再試行しない、§9.9） |
| 保持者が全員ルーム不参加 | サムネイルをグレースケール化、未取得本体の取得不能表示（§5.5） |
| 同一プロファイルで同一部屋に重複ログイン試行 | セッションは 1 つのまま、ミラータブとして参加表示（§9.12） |
| 設定/状態の同時更新要求（多タブ） | `store_tx` で直列化、処理者タブで read-modify-write（§11.1） |
| 処理者タブ閉鎖 | ハートビート失効（6s）で他タブがロック取得・次処理者へ自動引き継ぎ、委譲待機要求は再送（§11.1） |
| 同一プロファイルで同一部屋に重複ログイン試行 | 2 つ目のセッションは開始せず、ミラータブとして参加（§9.12）。別 uid はログアウト後 |
| セッション所有者タブ閉鎖 | 失効検知でミラータブがセッション権取得・同一 uid 自動再参加（§9.12） |
| 自身と異なる `xorig` の `C` 受信 | 無視 + 警告表示（作成後 `xorig` 変更不可、§6.6） |
| 部屋再作成後の旧参加者（旧作成者含む）ログイン | 既存メンバー全採決 NOK → ログイン不可（先にログイン済み勝ち、§6.9）。旧作成者には「別の管理者が部屋を立ち上げているようです」表示、room.json に `conflict` 記録で自動再参加禁止 |
| セッション中に `cr`/seedSaltedHash 不一致の `C` 受信 | 強制ログアウト（「部屋設定が再作成されました。再認証が必要です」、§6.9） |
| UTC 月境界到達（通常/同期セッション） | 自動で強制ログアウト（§6.7）。パスワード再入力でのみ再ログイン可 |
| サーバー参加中に `srvOn=false` の `C` 受信 | ただちに強制ログアウト・自動再参加しない（§6.8） |
| 自動 DL 台帳に h10 登録済み | 本体未取得でも再取得しない（台帳優先、§5.7）。クリアボタンで台帳リセット |

## 13. パフォーマンス見積り

- シート 1 枚: 384×768 JPEG q0.72 ≒ 30〜70KB → 4〜9 chunk ≒ wire 45〜100KB
- 本体 1 MB: gzip ≒ 0.9MB → 115 chunk → wire ≒ 1.25MB → 100ms 間隔で **約 12 秒**（LAN + Pico 実測で要検証）
- manifest 64 エントリ ≒ 3〜4KB（1 フレームに収まる、ページ分割は 65 枚超から）
- QR: 512bit pw + rid ≒ 130 文字 → QR バージョン 7 程度（PNG DL 軽）
- レンダリング窓: 月表示 3 ページ ≒ 90 日期セル、サムネイル数は日の投稿数依存。96pxサムネ + objectURL で窓内 3 ページ + 前後 1 ページの余裕をもっても DOM `<img>` は概算 300 以下・デコード後メモリ数 MB 級（窓外開放で抑止、§5.5）
- 一括 ZIP: 10MB / ZIP なら 2MB 画像 × 5 枚。エントリ単位で `CompressionStream('deflate-raw')` をストリーム変換し Blob parts を逐次連結するため、ピークメモリは 1 ZIP 分（約 10MB）+ 画像 1 枚に抑えられる（DEFLATE⇄STORE 比較で画像 1 枚分の一時コピーが増えるが ≤2MiB なので問題なし、§9.10）

## 14. 受入基準

1. 部屋 A を端末 1 で作成（パスワード設定/512bit 自動生成）、QR は**復号検証を通過したもののみ表示**される。端末 2 が QR（PNG DL→スキャン or ファイル読込 or 文字列ペースト）でログイン → 両者でルーム共有成立
2. 誤パスワード端末はデータフレームを一切交換できず、カレンダーも空（認証 UI 表示）
3. 端末 1 の共有画像のサムネイルが端末 2 の**カレンダー**に投稿時刻位置で自動表示（シート跨ぎ枚数でも）
4. 端末 2 がサムネイルクリック → 本体が端末 1 から転送されビューア表示（wire に `Q`/`H`/`~` chunk 列）
5. 端末 2 で「保存」→ 端末 2 の manifest に載り、端末 3 参加時に端末 2 が `Q` 応答者となりうる（拡散）
6. 同一画像を部屋 B でも共有 → `bodies/` のファイル数は増えず（`OPFS.ls` 確認）、`meta` の `r` 配列に部屋が増える
7. 「保存」後ページリロードで同一画像が OPFS から即表示（転送再発なし）、「DL」でダウンロード発生 + OPFS 保存維持
8. WS 切断 → カレンダー維持・保存済み画像閲覧/DL 可、未保存はエラー。再接続 → 再認証 → 差分同期でシート再取得なし
9. 全メッセージ < 16KB、close(1009) なし。複数タブ同時接続で各タブ独立動作
10. `GRID_*`/`CAL_VIEW` 上書き動作が仕様どおり
11. 同期モード: 端末 2 でトグル ON → 未所持画像が新しい順に自動取得され、フッターに `取得済み/取得対象` 表示。端末 2 のクリック取得中に自動取得が中断し操作後に再開される
12. 同一画像を 2 保持者が持つ環境で、複数回取得時に `Q` の `to` がラウンドロビンで切り替わる（wire 観測）
13. 取得中に保持者端末のプロセスをkill → 約 10 秒でウォッチドッグが発火、転送が別候補（無ければエラー）でやり直される
14. 削除 → カレンダーから消えゴミ箱に出現（`X` で受信者側もゴミ箱）→ 個別削除/空にするで即物理削除（`OPFS.ls` で bodies 消滅確認）、30 日超過スイープも確認（時計mock）
15. 保持者が全員退出した画像のサムネイルがグレースケール + バッジ表示
16. 一括 DL: 10MB 単位で ZIP 分割、ファイル名 `<部屋rid>-<yyyyMMddhhmmss>-001.zip` 形式、日本語ファイル名エントリが Windows/macOS 標準展開で文字化けしない（bit11 + Unicode extra 確認）、DEFLATE エントリが正しく展開できる（STORE 併存時も可）
17. ヘッダーの OPFS 使用量表示が共有/削除/ゴミ箱操作後に更新される
18. 月表示でスクロール中の DOM `<img>` 数が `CAL_WINDOW_PAGES` + 余裕（前後 1 ページ）相当を超えない（窓外解放の確認）
19. 設定変更 → ページリロード後も `user_settings.json` 経由で維持される（同期モード状態は `app_state.json` 側に記録）
20. QR 復号検証ループ: 強制検証失敗ケース（モック）でスペース付与→再エンコード→検証成功後に表示されること。上限超過時はエラー表示 + 文字列コピー提示
21. クロスオリジン: `xorig=true` の部屋で、別オリジン（別ポート配信の同一 HTML）の参加者が許可リストに追加後ログイン成功、リスト外オリジンは全メンバー不 OK でログイン不可。`xorig=false` の部屋では別オリジン参加が常に不可（リストが自オリジン 1 個に強制上書きされる）
22. 全メンバー採決: メンバー 3 名中 1 名が `ok:false` の場合ログイン失敗。1 名オフラインで応答なしの場合も失敗（`W` 再送後）
23. 2タブで同一部屋に参加し、同時に変更する操作（モード切替・設定変更）を行っても更新が消失せず、`user_settings.json`/`app_state.json` が直列に更新される。処理者タブを閉じても他タブで継続更新できる
24. プロファイル単一セッション: 同一ブラウザの 2 タブで同一部屋を開いても WS セッションは 1 個（サーバー側の入室表示は 1 uid）、ミラータブの操作が所有者経由で反映、いずれかのログアウトで全タブログアウト、所有者タブを閉じると残りのタブが同一 uid で自動再参加
25. `xorig` は作成時選択後変更不可（UI 無し）、他端末が `xorig` 変化を伴う `C` を送っても無視+警告。`xorig=true` のとき oa 追加のみ作成者に操作可
26. サーバーモード: ログイン画面で選択 → 自動同期が常時 ON、参加者一覧・過去参加者一覧（history.json）・OPFS 使用量（全体/部屋別）表示。ブラウザ再起動で自動再ログイン、ヘッダーのモードトグルは無効
27. 期間ソルト: 通常モードのログインは現在 UTC 月ソルトでのみ成立。UTC 月境界（テストではクロックモック）で自動ログアウトされ、パスワード再入力なしの再ログインは不可。サーバーモードのセッションは月境界を跨いでも維持され、`pwSalt`（参加日）で再参加できる
28. `srvOn`: 既定 false（ログイン画面でサーバー選択肢 disabled）。作成者が ON → サーバー参加成立、参加中に作成者が OFF → サーバー端末は即ログアウト（全タブ波及・自動再参加しない）、再度 ON で再参加可
29. 自動 DL: ON のサーバーモードで新着画像が自動で bodies+meta 保存され、`autodl.json` に h10 が登録される。bodies を消しても台帳登録済み h10 は再取得されない。クリアボタン後、同一 h10 が再取得・再登録される
30. seedSaltedHash 採決: 自動再参加メンバー（平文非保持）も採決に参加でき、月跨ぎ後は全メンバーが新パスワードで再ログインするまでいずれのログインも不成立（salt 不一致）、再ログイン成功後は保管値照合で成立
31. 部屋再作成競合: 作成者端末をクリアし同一部屋名で新規作成（新規パスワード）→ 旧作成者のログインは拒否され「別の管理者が部屋を立ち上げているようです」表示・`conflict` 記録・自動再参加不可。新旧どちらが先にログイン済みでも後発側が不成立（強制ログアウト）
32. ゴミ箱と同期: ゴミ箱入り画像は新しい同期対象になっても当該端末では無視（自動 DL 含む）、ゴミ箱から物理削除後は再び同期・自動 DL される
33. i18n: 言語設定（auto/ja/en）で全 UI メッセージ・エラー表示が切り替わる。ja/en 言語パックのキー集合が一致（欠落キーは表示時に警告 + フォールバック文言）

## 15. ブラウザ必要条件

- WebSocket / Canvas 2D / `URL.createObjectURL`

**v0.5 で決定済み**

- QR は `wwwroot/modules/qrcode.es.min.js` で生成し、`wwwroot/modules/jsQR/jsQR.es.min.nosjis.js` で復号検証する（生成→jsQR 復号→失敗時スペース付与再エンコードの検証ループ必須、§2.1/§6.4）

**v0.7 で決定済み**

- 認証成功者はパスワード（セッションメモリ）と許可オリジンリストと pwHash を保持（§6.6）
- 設定/状態の複数タブアクセスは `store_tx.js` の単一処理者トランザクションで直列化（§11.1）
- 設定ファイルはユーザー設定（`user_settings.json`）とアプリ状態（`app_state.json`）に分離（§10, §11）

**v0.8 で決定済み**

- 部屋ログイン/ログアウトはブラウザプロファイル単位で 1 セッション（所有者タブ + ミラータブ構成、§9.12）
- `xorig`（単一/マルチオリジン）は作成者のみ・作成時確定で作成後変更不可。マルチ時は oa 管理のみ作成者操作（§6.6）
- サーバーモード追加: ログイン画面でのみ選択（切替はログアウト要）、自動同期常時 ON、参加者/過去参加者一覧、OPFS 量表示（§5.7）

**v0.9 で決定済み**

- pwHash は期間ソルト付き（通常/同期: UTC `YYYYMM`+uid+オリジン → **月境界で強制ログアウト・パスワード再要求**、サーバー: 参加日 `YYYYMMDD`+uid+オリジン → 免除）（§4, §6.7）
- 採決は既存メンバー全員が応答（平文保持資格制限付き方式は v1.0 の seedSaltedHash 保管照合方式に置換、下記）
- サーバーモード許可 `srvOn` は作成者専権で**随時 ON/OFF 可**、OFF 時参加中サーバーは強制ログアウト（§6.8）
- サーバーモード自動ダウンロード（ON/OFF 可、既定 OFF）: 専用台帳 `rooms/<rid>/autodl.json`（h10）で DL 済み無視、クリアボタンで再実行（§5.7, §10）

**v1.0 で決定済み**

- pwHash は seedSaltedHash（平文 + 部屋名 rid + オリジン + 期間 salt）に確定。ログイン時に OPFS 保管、再参加・採決は**保管値照合**で行う（平文保持資格制限は廃止、全メンバー採決、§4/§6.2/§6.7）
- ゴミ箱入り画像は新たな同期対象でも当該端末では無視。ゴミ箱から物理削除後は再び同期（§9.9）
- 作成者端末消失後は同一部屋名再作成 + 新パスワード再発行で復帰。**先にログイン済み勝ち**（後発は強制ログアウト）、旧作成者には競合メッセージ、room.json に `conflict`（§6.9）

## 15. v1.1 追加仕様

### 15.1 QR タブと URL 共有
- 部屋ビューは作成者のみ表示されるサブタブを持つ: **画像 / URL QR / パスワード QR**。
- URL QR の内容は参加 URL `http://host:port/img_room.html#<部屋名 b64url>`（§5.1 のハッシュ参加と同じ形式。`encodeURIComponent` 適用）。
- パスワード QR は §8.4 の認証 QR（`TMIWR1:<部屋名>:<平文 pw>`）。平文 pw を保持する作成者セッションでのみ生成可（§6.4）。非保持時は引导メッセージ。
- **サーバーモード参加者は部屋ビューに URL QR を常時表示**（サブタブとは独立。コピペ・PNG DL 可）。

### 15.2 参加者バッジ列と参加時刻
- 部屋名下に参加者バッジ列を描画。**参加時刻（UnixTime, ms）の昇順**。自バッジは強調枠。
- サーバーモード参加者のバッジには **S マーク**。モードは J フレームの `md` フィールドで伝搬（`normal|sync|server`）。
- 参加時刻の相互通知（リレーは時刻を付さないと仮定したアプリ層プロトコル）:
  - メンバーは新規 J（未既知 uid）を検知すると折返し `J {to, uid, at, me:{uid,t,md}}` を返す。`at` = その J を観測した時刻、`me` = 自己紹介。
  - 受領側は自身の参加時刻を `at` の最小値で確定し、`me` を参加者表へ取り込む（既知メンバーの参加時刻もこれで補充される）。
  - 折返し J はデータ系フック（M 再周知等）を発火しない（`to` 付きはセッション内で消費）。
- 参加者表の `t`（参加時刻）は**初観測で確定**し、以後の J で上書きしない（v1.0 までは接触毎更新だった）。

### 15.3 部屋単位のアップロード上限 `mx`
- 単一画像の上限 bytes を `room.mx` として room.json と **C フレーム**（`mx` フィールド）で保持・配信。既定（`mx`=0/不在）は `CFG.MAX_IMG_BYTES` = **10 MiB**。
- 作成フォームに上限入力（MB、1〜200、既定 10）。作成者は再ログイン時と設定変更時に C を再配信。**新規参加者には J 検知時に作成者が C を再送**し、mx/srvOn 等を後から教える。
- 超過共有は `{error:'tooBig'}` → トーストに上限 MB を表示。

### 15.4 ビューア改訂
- モーダルタイトルは**ファイル名**（デコード済み meta.n）。ハッシュの表示行は廃止。
- 画像は **表示幅（fit: 幅 100%/高さ上限）⇄ ネイティブサイズ（実寸・折返しスクロール）** 切替。現在サイズ/ネイティブサイズ（px）を併記。
- **保存ボタン廃止**: 表示経路（本体取得完了時）に OPFS 本体保存を自動確定する。DL のみ残る。
- ゴミ箱ボタンは操作行の**右端**。閉じるは **☓（右上）**・Esc・背景クリック。共通 dlg() に統一。

### 15.5 样式の外出し
- 全样式は `wwwroot/css/imgroom.css`。色・枠線・角丸等は `:root` のテーマ変数（`--ir-bg` 等）で差し替え可能。
- JS は**クラス名のみ**で装飾を切り分け、設定値由来の寸法（サムネイルサイズ等）は CSS 変数（`--ir-thumb`）を JS から注入する。動的状態（表示/非表示・プログレス幅）のみインラインStyle を許容。

### 15.6 実装上の追補（サーバー・認証）
- サンプルリレー `Chat.leaveRoom` は**socket 実体一致**で部屋条目を削除する（userId 一致削除だと、旧接続の close イベント遅延到達が同一 userId の再ログインセッションを追い出すすれ違いが起きる）。
- サーバーモードの seed 塩は常に**月塩**（保管 seed と一致させる）。日付塩 `YYYYMMDD` は採決 W/at の使い捨て塩のみ（v1.0 の saltServer() seed 導出はcreator 単独再ログインを成立させないため改訂）。

### 15.7 v1.2 追補（ビューア・QR）
- **メタ 3 行**: 画像下は (1) 投稿者・部屋 (2) 投稿日・MimeType (3) SHA256Sum の 3 行のみ。SHA-256 は保管されない（内容アドレスは h10）ため、ビューア表示時に取得バイトから `crypto.subtle.digest` でその場計算し 16 進 64 桁で表示（非安全コンテキスト等では `(N/A)`）。
- **ズーム 6 段**: 表示幅（既定）/1/4/1/2/ネイティブ/2倍/4倍。選択中のボタンは `.ir-btn.on` で明示。倍率段は img の幅をネイティブ基準の実ピクセルでインライン指定し、ラッパの `.zoom` クラスで max 制限を外す（寸法のみ JS、見た目は CSS の原則維持）。
- **QR エリア**: QR 画像（`.ir-qrpic`）と URL 欄・コピー/PNG ボタン・説明（`.ir-qrnote`）を `.ir-qrrow` で横並び。URL QR には「スキャンすると部屋名入力済みの参加画面が開く。参加にはパスワードが必要」を併記。
- **パスワード QR**: 秘密鍵色系テーマ変数 `--ir-sec`/`--ir-sec-bd` の独立枠（`.ir-secret`）に収め、平文パスワードである旨の警告とスキャン挙動を記載。URL QR とは別枠・別色で明確に区別する。
- **ビューア単一化**: 同一画像の再クリックは無視、別画像表示時は既存ビューアを閉じる（モーダルの多重防止）。
- **`Vw.tC(e, cls, force)`**: 第 3 引数（force）を正式サポート（省略時はトグル従来通り）。選択状態クラス（`.on`）のトグル取り違えバグの修正を兼ねる。

### 15.8 v1.3 追補（一時退避とサーバーモード低メモリ化）
- **一時退避（hibernate）**: アプリは長時間作動するため、起動から `HIBER_AFTER_MS`（既定 12 時間）を超えたら、一時情報（`{rid, nb, uid, mode, pw?}`）を暗号化して localStorage へ書き出し、`location.reload()` する（`modules/imgroom/hibernate.js`）。経過は 60 秒間隔チェック+`visibilitychange` で検知（背景タブのタイマ鈍化対策）。退避は安全点（モーダル表示中・アップロード共有中・送受信転送中・pump 中でないこと）で行い、`HIBER_WAIT_MAX_MS`（既定 5 分）で強制。複数タブの同時リロードを避けるジッタ（最大 30 秒）。
- **暗号化と保管**: AES-GCM 256。鍵（256bit 乱数）は sessionStorage（タブ固有・リロードでは保持、タブを閉じると消滅）に置き、localStorage（同一オリジンの全タブ共有）には暗号文のみをキー `ir.hiber.v1.<tabId>` で保存する。tabId は sessionStorage の乱数識別子で、リロードを跨ぎタブクローンへは移らないため、**復号は同一タブのリロードでのみ可能**。平文パスワードを作成者タブが保持している場合のみ退避情報に含める（復帰後も pw QR・C 再発行が可能）。
- **復帰と有効期間**: ブート時 `restore()` は自タブ条目を即座に消費（削除）し、`at` から **5 分（`HIBER_TTL_MS`）以内**なら復号して自動復帰（home スキップ → `tryResume`: openRoom → `session.rejoin()`（seed 採決）→ 不可なら保管 pw で login → 不可ならその部屋のログイン画面）。超過条目は廃棄し通常起動。他タブの条目は生存中の退避を消さぬよう期限切れ分のみ掃除。非安全コンテキスト（`crypto.subtle` 無）では平文を残さないため書き出しをスキップしリロードのみ（復帰は autoJoin 等従来経路）。リロード前の `AppSettings.flush()` で OPFS 状態を確定させる。
- **サーバーモード低メモリ化**: `SliceCache` に LRU 上限（通常 64・サーバーモード 8。`SCACHE_MAX`/`SRV_SCACHE_MAX`、get で touch）。「G 再送待ち」の完了送信 chunks 保持 `outDone` をサーバーモード 10 秒へ短縮（`G_HOLD_MS`/`SRV_G_HOLD_MS`）。ビューアは SHA 計算用 ArrayBuffer を計算後即解放、モーダル閉じ時に `img` の src 属性を除去しデコード済みビットマップを解放（表示はサーバー既定 CSP `img-src data:` の制約で data: URL のまま）。取得の直列単一フライト（§9.3.7）とカレンダー窓レンダリング（§5.5）は既存のメモリ抑制策として維持。
- **protocol 修正（v1.3 伴う）**: 名乗り折返し `J{to,...}` を**無条件化**（§8.3）。ページ更新（退避復帰・手動リロード）ではリレーが退出を通知しないため他メンバーの roster に再参加者が残り続けて `isNew` ゲートでは折返しが起こらず、再参加者側の roster が補充されない不具合があった。折返しは `to` 自宛のみ処理で伝播しないためループなし。折返しに含まれる参加時刻 `at` で再参加者の既存参加時刻も維持される。
- **テスト**: `browserTest/tests/img-hiber.mjs`（11 チェック: 参加者側/作成者側の即時退避→リロード→自動再参加・roster 補充、localStorage 条目と sessionStorage 鍵の消去、復帰後の二重退避なし・タイマ再武装、tabId 安定、pw QR 復活（平文 pw 復帰）、有効期間超過条目（10 分前）は無視・削除）。

### 15.9 v1.3.1 中間チェック（XSS・メモリ監査）
- **XSS 監査結果（クライアント）**: `innerHTML`/`insertAdjacentHTML`/`document.write`/`DOMParser`/`eval`/`new Function` は wwwroot 全体で 0 件。ユーザー制御文字列（部屋名・uid・ファイル名・C/M フレーム・QR 結果・補間値）は全て `textContent`/`setAttribute`/`.value`/`.title` の安全な sink にのみ到達。**脆弱性 0 件**。この安全性は「innerHTML ゼロ」運用規約に依存するため、今后も innerHTML 系 API の使用を禁止する。
- **クライアント修正（v1.3.1）**:
  - `RoomSession.destroy()`（新設）: `leave()` 後に呼び、`BroadcastChannel` を閉じ（leave で postMessage 済みの配送のため close は次 tick、`onmessage` は `_dead` で即時無効化）、`_ev` 購読・`onFrame`・`transfer` 参照・`_hist`・`_lgPend`/`_histT` タイマを解除。これでログアウト→再ログイン毎に旧 ctx グラフ（`collection.metas` 全件等）が BC を GC 根として永久残留していた（最大級）。
  - `disposeRoom()`: `session.destroy()`・`transfer.destroy()`・`_mTmr` clear・`peerMap.clear()` を追加。
  - `SheetRoom.rebuild()`: 末尾で `thumbs` を現 manifest h10 集合外で削除（投稿毎の Blob キャッシュ無制限成長防止）。
  - `scanFlow()`: `QRScan.camera` は async（Promise）であるため `then` で `stop` を確実に保持し、☓/Esc/背景/done の全閉経路（`_onClose`）でカメラ+rAF+復号ループを停止。従来は stop を取得できずカメラが無限稼働、かつ成功時も「カメラ不可用」表示になる機能バグだった。

### 15.10 v1.3.2 低スペック・低メモリ実測（browserTest/tests/img-perf.mjs）
- 手法: headless chromium + CDP `Performance.getMetrics`（JS heap/Nodes/JSEventListeners/TaskDuration/Layout）+ `HeapProfiler.collectGarbage` 強制後スナップショット + アプリ内部 Map サイズ + `Emulation.setCPUThrottlingRate(4x)` で低スペック模擬。シナリオ: 起動→部屋作成→**41 画像共有**→カレンダー窓→大画像(2.6MB)ビューア→一括 ZIP→ログアウト/再ログイン×3→リロード(41 件 boot)→4x スロットル再表示。

## 17. 追加仕様 v1.4: 大きな画像・形式ポリシー（投入ゲート）
- 適用箇所: 共有入口（room_app のファイル input セクション）。**collection.share 等のプログラミック経路には適用されない**（テスト・内部処理は従来通り）。
- 規則（この順で判定）:
  1. **ブラウザ非対応形式 → 上記以前にお断り**: MIME がホワイトリスト（png/jpeg/webp/gif/bmp/avif）に無いファイルは確認ダイアログすら出さず Toast でお断り（TIFF 等）。変換試行中のデコード失敗（実質非対応の実体）もお断り。
  2. **256MB 超の検知 → お断り**: ファイル自体が 256MB 超、またはヘッダのみ（先頭 64KB）から寸法を推定し `w×h×4 > 256MB`（≈64M ピクセル超）と**確定できる**ものは共有しない。ヘッダ推定不可（VP8L 等）は次の変換時のデコード成否で判定（デコード不可=お断り）。
  3. **上限超（部屋 mx、既定 10MB）→ 確認**: 「長辺 4096px 以内への縮小 + JPEG 再圧縮（品質 82%）で共有してよいか」を確認（window.confirm）。承諾で変換（ImgProc.shrink）→ 変換後（.jpg）を共有・サムネイル化。拒否でスキップ。変換後が部屋 mx を Still 超なら collection.share の tooBig で最終拒否。
- 実装: `ImgProc.sniffDims`（PNG IHDR / JPEG SOF スキャン / GIF / WebP VP8・VP8X / BMP / AVIF ispe のヘッダ解析）と `ImgProc.shrink`（load→canvas→toBlob jpeg、デコード失敗 null）。locale キー: msg.share.unsupported / msg.share.tooBig / msg.share.over。
- 検証（img-spec §16 セクション + probe）:
  - TIFF 1MB → ダイアログゼロでお断り、metas 不変 ✓
  - PNG ヘッダ 9000×9000（11MB、推定デコード 324MB）→ ダイアログゼロでお断り ✓
  - mx=1MB 部屋で 1.5MB jpeg → 確認表示（文件名+4096 句）→ 辞退でスキップ ✓
  - mx=1MB 部屋で 900×900 ノイズ PNG(1.7MB) → 承諾 → jpeg ~0.4MB に変換共有、meta.t=image/jpeg・l≦mx、**保存本体が復号可（閲覧可能）** ✓
  - mx=10MB 既定部屋で 13.1MB PNG → 承諾 → 2.6MB jpeg 変換共有（probe 実測、shrink 1.07s）✓
- メモリ安全性: ヘッダ推定は 64KB のみ読込。デコードは 256MB 超確定段階で先行拒否するため、変換のためのフルデコードは 256MB 以内に収まる対象のみ実行される。

## 18. 試算: スマホ 1 タブ × 10 万画像部屋（v1.4 現状実装）

## 20. 追加仕様 v1.6: サムネイル正方形 contain と表示サイズピッカー

### 仕様
- **生成/交換基準 = 128×128 正方形 contain**: `ImgProc.thumb(blob, 128)` は center-crop 廃止。画像**全体が収まる**よう等倍縮小し、短辺側は白レターボックスで中央配置。元画像が 128 満たない場合は**長辺が 128 になるまで拡大**。共有時(`room_app`)・body 遅延生成(`room_calendar.genFromBody`)・シート交換(`sheet_room`)のサムネイルはいずれも 128 基準で生成・保存・交換する。
- **表示サイズ = 32/64/96/128（既定 64）**: 画面**上部**（モード切替と同じツール行）と**下部**（カレンダーの下）に `32/64/96/128` ピッカーを設け、どちらからでも変更。選択値は `user_settings` に `THUMB_PX` として永続（次回起動時も同一）。2 箇所のピッカーは選択表示(`.on`)が同期する。
- 表示だけ変える: 基準 128 の画像を CSS 変数 `--ir-thumb` で縮小表示（スライス/シート再生成なし・SliceCache 保持のまま即時切替）。`setThumbPx` で CalView を cellPx(=THUMB_PX+24) 付きで再構築し、セル高さ/プレースホルダ高さも追従。

### 保存形式への影響
- シートファイル名に基準 px を焼き込む: `rooms/<rid>/sheet/<uid>_<idx>.s128.<h>`。scan 時に px 不一致/旧形式（px なし）のシートは失効として削除し、再生成で新基準版に置換される。

## 33. 追加仕様 v2.7: 「パスワードまたはオリジンが違います」の原因整理と QR 貼付け耐性
質問（2026-11-11）: エラー `msg.auth.fail`「パスワードまたはオリジンが違います」が出る。QR 認証 QR をコピーすると付いてくる **TMIWR1: はパスワードの一部か?**

**回答**:
1. **TMIWR1: はパスワードの一部ではない**。§5.5 の QR データ形式のプレフィックスで、認証 QR の内容は `TMIWR1:<部屋名b64url>:<パスワード>`（`qrPack`）。パスワード本体は最後の `:` の後ろ（自動生成値は b64url 512bit で `:` を含まない）。
2. エラーの 2 原因（`msg.auth.fail`＝採決不 OK、§6.2/§12）:
   - **パスワード不一致**: パック文字列（TMIWR1:…）や他部屋のパスワードをそのまま入力していた。→ **v2.7 対策**: ログイン/作成/再試行のパスワード欄はパック・プレフィックスを**自動認識して除去**（`RoomApp.pwFromField`）。QR のコピーをそのまま貼付けても認証できる。
   - **オリジン不一致**: seed は `H(パスワード, 部屋名, **Web ホスト origin**, salt)`（§4/§7.3）。同一パスワードでも **127.0.0.1 と localhost と LAN IP は別オリジン**で seed が違う。対策は (a) 作成時と同じ URL（部屋 URL QR をスキャン）で参加、または (b) §6.6 で作成者がクロスオリジン許可を有効化し許可オリジン管理（oa）に参加側オリジンを登録。§32 のとおり WebSocket 接続先オリジンはこの判定に関与しない。
3. **UI 追加**: 認証 QR の下に「**パスワードのみコピー**」ボタン（パックでなく本体だけをクリップボードへ、トースト確認）と説明注記「TMIWR1:… はデータ形式で、TMIWR1: はパスワードの一部ではありません」を QR パネル/部屋メニュー双方に設置。

### 実装
- `room_app.js`: `pwFromField`（tryLogin/doCreate 経路で適用。retryBox は lastTry 経由で自動カバー）。`pwCopyRow`（qrPanel qrpw と roomMenu QR 欄）。
- locale: `btn.copy.pw`/`msg.copied.pw`/`qr.pw.note`（ja/en）。

## 34. 追加仕様 v2.8: 認証失敗の切り分け（診断表示）— 「WebSocket で名前は取れているのに msg.auth.fail」
状況（2026-11-12 の報告）: WS リレー接続は成功し参加者名（J）は見えるが、採決が不 OK で「パスワードまたはオリジンが違います」(`msg.auth.fail`)。

### 検証の 3 段（`_checkW`、§6.2）と原因の ranked 切り分け
1. **salt 妥当性**: 通常/同期は「現在 UTC 月」、サーバーモードは `YYYYMMDD` 当日以前かつ `srvOn=true`。**サーバーモードでsrvOn=false の部屋に参加**→即不 OK（§6.8）＝同じエラー。
2. **オリジン整合**: `xorig=false` の部屋では**各既存メンバーは自分の `location.origin` 1 個のみ許可**（`_effOa` 強制）。したがって `127.0.0.1` と `localhost` と LAN IP（例 `192.168.2.14`）とドメインは**すべて別オリジンで不 OK**。複数メンバーがいる部屋では**1 名でも不 OK を返すと失敗**（§6.2）—「名前は見えるのに失敗」の最頻原因。対策: (a) 部屋 URL QR をスキャンして**作成時と同一 URL**で参加、(b) 作成時にクロスオリジン許可（xorig）を有効化し、**許可オリジン管理（oa）に参加側のオリジンを登録**（xorig=true で oa 空だと既存メンバー自身のオリジンも oa に無いと不 OK になりうるため登録必須）。
3. **パスワード整合**: 各メンバーは**自 OPFS 保管 seed** で `at` を再計算照合。部屋メニューの**パスワード発行**で seed は C 配信で更新されるため、**旧パスワードでの参加は不 OK**。他デバイスで OPFS が分かれていると作成者の seed と突き合わせられるのはメンバー経由のみ。
4. その他: 同名の**別部屋**（別のブラウザで同じ名前で再作成→別 seed）、`HASH_ROUNDS` の設定差異（URL クエリ上書き・user_settings）、貼り付けに混入した空白（v2.7 でパック/末尾空白は除去済み）。

### 診断表示（クライアント追加・自機情報のみで秘密は露出しない）
- **参加フォーム**: パスワード欄の下に「このページのオリジン: <origin>」を表示（作成者に oa 登録を依頼できる）。
- **リトライボックス（authFail 後）**: 診断情報としてこのページのオリジンとモード、および対処（同一 URL 参加/xorig+oa 登録/パスワード発行後は新パスワード）の注記を表示。

### テスト（「SPEC OK」）
- `joinFormOriginLine`（参加フォームにオリジン表示）/ `retryDiag`（誤パスワード参加→採決不 OK→リトライボックスに「診断情報:」「このページのオリジン: http://」「モード: normal」と対処文言）。
- 運用注意: テスト実行には SampleServer(:8080) が必要（停止時は `npm run server` 相当で再起動）。
- 修正（回帰中判明）: **キー送り `slStep` は隣接項目が実体欠損でも同方向の次候補へスキップ**（fsKeyNext の flake はこの穴が原因）。送り停止方針（§22「実体を取り出せない項目は進めない」）はタイマ送りの `slNext` のみ。

## 38. 追加仕様 v2.11: seed から origin を除去 — クロスオリジン参加(xorig)の実際の成立
調査経緯（ユーザーログ 20261111c/20261112b + `.tmp/atcalc.mjs`）: panco は **GitHub Pages（`https://ryunosinfx.github.io`）**でページを開き、接続設定（§29 の WSBASE）でローカル SampleServer に WS 接続。ponta はローカル(origin 別)。3 要素（URL・部屋名 testa・パスワード）を再計算したところ**ログの ho/hor/at と完全一致** → panco の入力は正しく、拒否は**ponta 保管 seed との不一致**と確定。

### 判明した設計上の穴（v2.10 まで）
- seedSaltedHash が `H(pw|部屋名b64url|**ページ origin**|salt)` で origin を含むため、**投票者は自分の seed でしか at を再計算できず、別オリジンの参加者（別 origin で seed を計算）の at は永久に一致しない**。§6.6 の xorig/oa は検証 2 を緩和するが検証 3 が残るため、**xorig を有効にしても別オリジン参加は成立しなかった**（テストにも未覆盖）。
- 同時に、検証 2 の `ho/hor` は参加側申告値であり seed の origin 束縛も「正しい pw を持つ者」には同一 URL 前提で自明。**origin 束縛は実効的な追加防御を持たず、正当な別オリジン利用者だけを失敗させていた**。

### v2.11 の変更（クライアントのみ）
- `AuthChallenge.seed(password, ridB64U, salt, rounds)` → **`H.d(password + '|' + ridB64U + '|' + salt, rounds)`**。呼び出し 3 箇所（doCreate / 再発行 / `_seedOf`）から `location.origin` 引数を削除。
- オリジン統制は **§6.2 検証 2 のみ**（xorig=false → 各メンバーの自オリジン 1 個、xorig=true → oa に列挙されたオリジンの ho/hor と一致）。これで §6.6 の記述どおり **xorig=true + oa 登録の部屋では別オリジン参加が成立**し、xorig=false は従来どおり別オリジンを拒否。
- **互換性（破壊的）**: v2.10 以前の seed（origin 込み）を保管する既存部屋は、v2.11 クライアントと一致しない。対処は (a) 作成者が**パスワード発行**（新 seed 生成・C 配信で全成员更新）するか、(b) 部屋を作り直す。**自動マイグレーションは持たない**（§15.9 のサーバー不変方針の下、保管 seed からの式変換は平文不在で不可）。
- **解決確認（2026-11-13 00:2x、20261112e.log）**： e.log の at は新旧どちらの seed 式でも c.log 三点セットから再現できず、**試行されていた「部屋名+パスワード」が投票者（ponta）の Pages 側部屋のものでない**と確定（ローカル URL 発と同 Pages URL 発は同名でも別部屋・別パスワード。OPFS はブラウザ×URL 単位）。以後の手順で接続成功：**両端末を同一の Pages URL で強制再読込 → 片方が新規名で部屋作成 → もう片方がアプリの「QR 読取」で作成者の認証 QR をスキャン（部屋名+パスワード自動入力）→ 採決通過で入室**。人的な取り違えを構造的に排除する経路として推奨。
- **seedV 版印（20261112d.log の運用観察で追加）**: OPFS の room.json はクライアント更新で書き換わらないため、更新前クライアントが作った部屋の seed（旧式）が残り `gate=pw` で失敗する事例を確認。以後の保存（`_saveRoom`/`pushC`）は **`seedV: 2`** を刻み、ログイン時 `room.pw` あり & `seedV !== 2` ならトースト `msg.seed.legacy`（単独入室→パスワード発行→新パスワードで参加、の案内）を表示。既存の旧 room.json は自動検出・案内のみで自動変換しない（平文不在で変換不能のため）。

### ユーザー環境（panco@GitHub Pages ↔ ponta@local）の正しさの筋
1. 両側を v2.11 クライアントへ**強制再読込**（キャッシュ注意）。
2. ponta が部屋を**クロスオリジン許可 ON で再作成**（xorig は作成時固定 §6.6）。

## 40. 追加仕様 v2.13: モード keep（通常・取得保持）
要求（2026-11-13）: 通常モードを 2 種に分ける。**通常（都度取得）**=現行（画像本文はそのつど保持者から P2P 取得）。**通常（取得保持）`= 一度取得した画像本文を OPFS に保存し、以降はローカルから表示する。

- **挙動（RoomCalendar.fetchBody）**:
  1. `keep` は**ローカル優先**: `store.get(h10)` に本体があれば転送せず即表示（全保持者不参加でも表示可。allDeparted のグレー Toast も出ない）。

  3. 取得失敗・採決等の他ゲートは normal と同一。
- **`Collection.adopt(meta)`（新 API・契約更新済み）**: 既存 meta を manifest エントリとして追加（`_manifestAdd` 再利用、meta 自体は書かない、重複は false）。

- **保存容量**: 取得保持は取得した分だけ OPFS 使用量が増える（usage メータ表示。自動削除はせず、ゴミ箱スイープ §9.8 は削除済みアイテムのみ）。
- **ビューアの自動保存（v1.x 追加仕様）との関係**: 表示時の store.put は全モード共通で従来通り。keep の違いは **manifest 採用＝保持者化とローカル優先表示**にある（都度取得では manifest に入らないため再取得になる）。

## 43. 追加仕様 v2.16: ビューアの両端クリックで前後切替・キー左右・ダブルで全画面
要求（2026-11-14）: 画像モーダル表示中に ①表示領域を 3 分割した**両端(左右 1/3)をクリック可能にして前/次の画像へ切替**(添付データも同様に従追) ②**キーボード左右**でも同様 ③**ダブルクリック/ダブルタップで全画面表示**。

- **切替順（v2.16）**: 部屋の**全項目（ゴミ箱除く）の ts 降順**（カルNDAR表示順と一致、slideshow の「保有のみ seq」とは別で**未保有も含む**）。未保有の次項目は開いた瞬間に通常の本文取得（§9.x P2P。keep モードならローカル優先）で表示、取得失敗時は同じ方向の次候補へスキップ（v2.8 §34 のキー送り方針を踏襲）。周回（末尾→先頭）。
- **クリック帯（`.ir-navz .l/.r`）**: 画像ラップ上に左右 1/3 幅のオーバーレイ（hover で矢印 ‹ › 表示、touch では常に薄く表示）。**単クリックは 300ms 遅延させて前後切替確定**、同一位置の連続クリック（ダブル）は切替を取り消して**全画面表示**へ。全画面モード中の帯タップは既存の送り（slStep・保有 seq）に接続。
- **中央のダブルクリック/ダブルタップ**: 画像中央部の 2 クリック（320ms 以内）で全画面表示（`enterFs`）。全画面中の中央タップは既存の解除確認（§22）。モバイルのダブルタップはクリック合成に依存（dblclick 非発火ブラウザでも 2 クリック間隔で検出）。
- **キー左右**: 従来は全画面のみ（v2.5 §30）。**v2.16 で全画面でなくても有効**（その場合は上記の全項目順で navStep）。`_vPend` 中（取得中）は viewer 多重防止が効く。
- 全画面/スライドショー（§22）やズーム・添付データ 3 行（§v1.2）はそのまま。開き直し方式なので**画像・添付データ（投稿者/部屋・投稿日/MimeType・SHA256）は常に表示中項目に追従**。

### テスト（「SPEC OK」）
- `navStart`/`navZones`（帯 2 個）/ `navNext`（右端クリックで次へ、P2P 取得込み 15s 待ち）/ `navMeta`（添付データ文本も変化）/ `navPrev`（左端で復帰）/ `navKeyR`（ArrowRight 同順）/ `fsDbl`（dblclick で ir-fs）/ `fsExitPanel`,`fsExited`（全画面解除経路は既存踏襲）。
